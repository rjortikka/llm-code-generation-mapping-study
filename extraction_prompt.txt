I am conducting a systematic mapping study on code generation by Large Language Models (LLMs). For each research paper I provide, please analyze it and extract information according to the following strict definitions and format.
Inclusion Criteria (1–7)
For each paper, state which of the following criteria are met. Provide a brief justification for each met criterion.
1.	Study creates a tool or method to enhance LLM code generation.
2.	Study evaluates and/or compares the code generation capability of LLMs (one or more models).
3.	Study evaluates something specific in LLM generated code (e.g., security, greenness, correctness, readability, maintainability, performance, etc.).
4.	Study evaluates a specific code language generated by LLMs (e.g., Python, Java, C++, etc.).
5.	Study evaluates the generation of code based objects (e.g., apps, APIs, smart contracts, unit tests, classes, functions, etc.).
6.	Benchmark evaluation model creation – the paper creates a new benchmark or enhances an existing one for evaluating LLM code generation.
7.	Literature is broader than just code generation by LLMs but still covers the topic (e.g., surveys, systematic reviews, or studies that discuss code generation within a wider context).
________________________________________
Core Definitions
•	Code Generation: Requirements → Correct Code (natural language description to executable code).
•	Code Translation: Code_A → Code_B (converting code from one language to another).
•	Program Repair: Buggy Code → Fixed Code.
•	Program Optimization: Non optimized Code → Optimized Code (must involve transforming existing non optimized code into a more efficient version; measuring efficiency of generated code is not optimization).
•	Code Completion: Predicting subsequent code as the developer types (interactive autocomplete).
Software Engineering Scope
The study must be strictly about software engineering. Exclude papers focused on hardware, Verilog, robotics, controller code, or IoT with physical devices.
Research Type
•	Academic: research conducted at universities / research institutes.
•	Industry: only if the tool/method was implemented and evaluated in an actual workplace setting. Industry co authors or funding alone do not qualify.
•	Both: if the paper clearly reports both academic research and a workplace deployment/evaluation.
Data Extraction Format
For each relevant paper, extract the following 18 fields exactly as described. If a field is not present in the paper, state that it is missing.
Study Context
1.	Research type – Academic / Industry / Both (see definition above).
2.	Software engineering tasks studied – list the tasks (e.g., code generation, test generation, program repair, optimization, etc.).
3.	Software engineering tools studied – list the evaluated or compared tools, including LLMs, frameworks, static analyzers, etc.
Technical Details
4.	Programming languages (or natural language) used (input) – e.g., English prompts, Java, etc.
5.	Programming languages used (output) – e.g., Python, Java, C++, etc.
6.	Size and nature of code being generated – e.g., function level snippets, full applications, lines of code, dataset size, etc.
7.	Datasets used for validation/training – names of datasets, sources, size, any filtering applied.
Evaluation
8.	Performance measures used – e.g., correctness, coverage, security violations, runtime, memory, etc.
9.	Evaluation metrics used – e.g., Pass@k, BLEU, CodeBLEU, precision, recall, F1, etc.
10.	Validation methodologies used – e.g., controlled experiments, user studies, ablation studies, statistical tests.
11.	Benchmarks used (if any) – list any benchmark names (e.g., HumanEval, MBPP, Defects4J). If the paper creates a new benchmark, note it here.
Findings
12.	Major challenges reported – problems, limitations, or difficulties identified in the paper.
13.	Solutions and best practices presented – proposed approaches, techniques, or recommendations.
14.	Limitations in the study reported – weaknesses or threats acknowledged by the authors.
15.	Research gaps identified – what is missing in the field that this paper aims to address (the empty spot they are filling).
16.	Future directions proposed – new empty spots created by this paper for subsequent research (explicitly stated or synthesized).
Extras
17.	New tool/tools developed in study – name and brief description of any new tool, framework, or method created.
18.	Purpose of that tool – what problem it solves and how it enhances LLM code generation (or related tasks).
Additional Notes
•	For research gaps vs. future directions: research gaps are what the paper itself tries to fill; future directions are what the paper suggests for later work.
•	Program optimization requires that the paper actually transforms existing non optimized code into optimized code (not just measuring efficiency of generated code).
•	When listing inclusion criteria, provide a short reasoning for each met criterion.
•	If a paper is excluded, state the reason clearly (e.g., not about code generation, conceptual only, no experiments, etc.).
